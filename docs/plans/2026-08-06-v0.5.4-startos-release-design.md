# Buzz v0.5.4 StartOS Release Design

## Goal

Replace the alpha snapshot-style package identity with the conventional StartOS
Extended Versioning identity for the selected official Buzz release, rebuild the
exact native packages, and publish them in a verified GitHub Release.

## Version Identity

The package tracks upstream tag `desktop-v0.5.4` at commit
`651f6372754e60e3f936b3397040eb0f1e44c9f3`. Its StartOS package version is
therefore `0.5.4:0`: `0.5.4` is the stable upstream release and `0` is the first
Community Registry wrapper revision. The corresponding immutable Git tag is
`v0.5.4_0`.

The previous `0.2.0-main...:2` package and tag remain historical alpha
artifacts. They are not moved or deleted. `0.5.4:0` sorts above every prior
alpha package, so the existing range migration remains sufficient.

## Artifact Boundary

One clean source commit contains the conventional version, release notes,
runtime pins, package behavior, and an unfrozen candidate template. Tag
`v0.5.4_0` points to that commit. Native x86_64 and aarch64 `.s9pk` files are
built and signed exactly once from the tag commit.

A later evidence-only commit changes the candidate to `FROZEN` and records the
tag commit, signer, archive sizes, and SHA-256 hashes. This avoids a recursive
artifact identity while preserving reviewable evidence on `main`.

## GitHub Release

The public release uses tag `v0.5.4_0` and contains:

- `buzz_x86_64.s9pk`;
- `buzz_aarch64.s9pk`; and
- `SHA256SUMS` covering both archives.

The release is created as a draft, its tag, target, assets, sizes, and uploaded
bytes are verified, and only then is it made public. It is not marked as a
prerelease because `desktop-v0.5.4` is a stable upstream release. Release notes
state that Community Registry device qualification remains pending and repeat
the documented Android/private-CA and remote-mobile limitations.

## Verification

Before tagging, run dependency signature and vulnerability policy checks, all
tests, formatting, TypeScript, Start SDK lint, immutable image verification,
device-evidence structure validation, and the JavaScript build. For each package
verify the manifest version, tag-source Git hash, SDK version, native-only image
tree, commitment, signer fingerprint, size, and SHA-256. After upload, download
the GitHub Release assets into a temporary directory and verify `SHA256SUMS`.
