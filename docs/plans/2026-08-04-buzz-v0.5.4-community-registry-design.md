# Buzz v0.5.4 Community Registry Preparation Design

## Goal

Synchronize the maintained Buzz companion-client fork and the Buzz StartOS
package with the latest stable upstream release, then produce an evidence-backed
Community Registry readiness decision without publishing or submitting anything
automatically.

## Selected Upstream Target

Use the upstream release tag `desktop-v0.5.4` at commit
`651f6372754e60e3f936b3397040eb0f1e44c9f3`.

This is a lightweight tag, so the tag itself has no independently verifiable
signature. GitHub marks the release as stable and reports that its target commit
was created by GitHub Actions with a verified signature. Record and verify both
the tag target and full commit identity before integration. The target is 96
commits newer than the currently packaged Buzz snapshot
`63496cc1d4c6f1b7c613801bdcc694169dcf391a`. The official multi-architecture
container `ghcr.io/block/buzz:sha-651f637` exists. Do not substitute the newer,
unreleased upstream `main`, a mutable `main` tag, or `latest`.

## Architecture

Treat the companion client and server package as separate downstream products:

- `buzz9` merges the upstream release tag with history preserved. Its desktop
  and `buzz-acp` native-root changes remain downstream client adaptations unless
  the release contains an equivalent verified implementation.
- `buzz-startos` continues to package the official upstream server image. It
  does not copy companion-client code into the server image. It updates the
  immutable image pins, package identity, runtime contract, tests, operational
  evidence, and documentation for the selected release commit.

Perform both updates on isolated branches and worktrees. Do not push either
branch, create a public release, send a submission email, or open a Community
Registry pull request until the final readiness review is approved.

## Companion-Client Integration

Merge the verified target commit of `desktop-v0.5.4` into the current
`mdubore/buzz9` main lineage. Review the four downstream-only commits and retain
only behavior that upstream has not replaced:

- native certificate roots for desktop WebSocket connections;
- native certificate roots for `buzz-acp` relay connections;
- the associated design documentation and merge history.

Resolve conflicts by preferring upstream application behavior while preserving
the required StartOS certificate compatibility. Re-run focused desktop and ACP
TLS tests, then the applicable repository checks and packaging commands.

## StartOS Package Integration

Audit the complete `63496cc..651f637` range before changing package pins. Review
all changes to:

- image user, entrypoint, commands, binaries, and exposed ports;
- relay, pairing relay, admin, database, media, Redis, and MinIO behavior;
- environment variables, secrets, bind addresses, and canonical URLs;
- PostgreSQL migrations and upgrade compatibility;
- persistent paths, backup authority, restore behavior, and ownership;
- health checks, startup order, resource requirements, and dependencies;
- authorization, membership, Git, NIP-11, pairing, ACP, and browser behavior.

Pin the OCI index and both native runtime manifests by digest. Verify each
architecture's image configuration without executing the foreign architecture.
Create a new immutable runtime-contract record for `651f637`; preserve older
records as historical evidence.

Keep the dedicated pairing WSS interface and the upgrade path from the installed
`63496cc:2` package. Use `startos/versions/current.ts` unless the audit identifies
a genuine package-level data migration that requires a new version vertex.

## Compatibility Boundaries

The release sync does not solve unmodified Android's rejection of the StartOS
private certificate chain. Documentation must continue to state that:

- Desktop and ACP need native-root-aware client builds for the local StartOS
  certificate configuration;
- the dedicated pairing endpoint fixes the prior HTTP 404 and supports a valid
  WebSocket upgrade;
- unmodified Android pairing is not supported by the current private-CA local
  configuration;
- public DNS with a publicly trusted certificate, such as a later StartTunnel
  or VPS design, is the intended long-term mobile path.

Do not weaken transport security, add an insecure WebSocket fallback, or modify
the mobile application as part of this release sync.

## Failure Handling

Stop the update rather than improvise if:

- the upstream tag or image no longer resolves to the recorded identities;
- native image metadata differs unexpectedly between architectures;
- upstream removed or materially changed a required command, port, environment
  variable, volume, migration, or health endpoint;
- the desktop or ACP native-root behavior cannot be preserved safely;
- a package migration cannot preserve existing data and configuration;
- tests, type checking, package builds, image verification, or vulnerability
  policy fail;
- required device evidence is unavailable or incomplete.

Record blockers explicitly in `TODO.md` and the final readiness report. A
successful compile or pack is not evidence of successful operation.

## Verification

For the companion fork:

1. Verify a clean pre-merge baseline.
2. Verify the lightweight tag target and merge that release commit with history
   preserved.
3. Run focused desktop and ACP TLS/WebSocket tests.
4. Run the applicable upstream tests, builds, and client packaging checks.
5. Inspect the final graph and downstream-only diff.

For the StartOS package:

1. Write or update failing tests for changed runtime and version assumptions.
2. Update immutable pins and runtime-contract evidence.
3. Run formatting checks, `tsc --noEmit`, the full test suite, image metadata
   verification, vulnerability-policy checks, and repository controls.
4. Build and inspect both architecture packages.
5. Exercise clean install, service start, UI access, health checks, Desktop and
   ACP connectivity, pairing QR generation, upgrade from revision `:2`, backup
   and restore, uninstall, and reinstall on stable StartOS hardware.

The final device checks must use the repository's evidence schema and preserve
independent review requirements. Unrun checks remain `NOT RUN` and block a
production-ready claim.

## Community Registry Boundary

Before initial submission, ensure:

- the public repository is current and contains no machine-local artifacts or
  secrets;
- the package follows StartOS tag conventions;
- type checking, tests, and pack steps are green;
- README describes every action, volume, port, dependency, and limitation while
  containing no version numbers;
- instructions and release notes accurately describe user-visible behavior;
- clean install, startup, UI, health, uninstall, and reinstall were verified on
  StartOS;
- all security and device gates required by this repository are satisfied.

Only after a reviewed go decision should the repository be pushed and emailed
to `submissions@start9.com`. Start9 will then fork it into the Start9-Community
organization. Subsequent changes go through pull requests to that fork; a merged
PR publishes to community-beta, and production promotion requires a separate
developer go-ahead.
